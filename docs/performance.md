# 性能调优

现象：隧道能用，但「慢」——小请求时不时卡 3~10 秒，单流下载只有 300KB/s 出头。

按收益排序，五个改动把「能用」变成了「好用」。

## 1. 流 ID 复用竞态（体感最差的那个）

原先 `allocIDLocked` 用 free 列表做 LIFO 复用，流一关就立刻把 ID 放回、下一个新流马上拿同一个 ID。对端此时旧流往往还没收尾，新 `OPEN` 帧落到 `m.get(id)` 命中的**旧流**上，被当成旧流的帧投进旧接收队列，再随旧流一起丢弃——**发起方永远等不到 `OPEN_OK`，只能超时**。

client 的 `openTO=3s`，表现就是「每个请求先卡 3 秒再成功」；旧版 `openTO=10s` 则更惨。

修法（`internal/mux.go`）：

- `allocIDLocked` 改为**单调递增不复用**（`uint32` 空间够用很久），删掉 free 列表；
- `readLoop` 收到 `OPEN` 且该 ID 仍存在时，**先 terminate + drop 旧流再接新流**。宁可错杀残留流，也不让新 OPEN 被吞。

> relay 侧的路由 ID 分配也有快速复用问题，方向相同（单调化）。client 侧已加 `-fin-guard` 兜底：关流前多等一会儿再发 FIN，规避串包。

## 2. 单 TCP 收发缓冲太小

隧道是长肥管道：本机↔中继 RTT 55ms 起，还夹着移动热点。系统默认几十 KB 的缓冲把带宽延迟积压死，单流实测只有 300~400KB/s。

`SecureConn.SetNoDelay()` 里把 `SO_RCVBUF` / `SO_SNDBUF` 放大到 **4MB**，单流立刻涨到 1.4~1.7MB/s。

## 3. `deliver` 阻塞共享读循环

原投递逻辑「recv channel 满就阻塞等待，最多 30 秒」。一条没人读的流（比如客户端已放弃的下载）会把唯一的读循环卡住，期间**同隧道所有新流都拿不到 `OPEN_OK`**。

改为「非阻塞入队 + 4MB / 1024 帧上限」，超限只重置那一条流。

## 4. 心跳与判死太慢

| 位置 | 原值 | 现值 | 影响 |
|---|---|---|---|
| home 心跳 / 判死 | 20s / 60s | 5s / 12s | 死连接最长存活从 1 分钟降到 12 秒 |
| client 池心跳 / 判死 | 15s / 45s | 5s / 12s | 同上 |
| client `-open-timeout` | 10s | 3s | 万一踩到死连接，只损失 3 秒 |

`Mux.IdleSince()` 用 `bornAt` 兜底，避免「刚建好还没收到帧」的新连接被当成万年无响应误杀。

## 5. 选路优先「刚有回包」的连接

`pick()` 不再无脑轮询，优先挑 `IdleSince() <= 6s` 的连接（心跳回包刚到的），全都不新鲜时才退化为「挑最不陈旧的」。

## 实测（Mac ↔ 公网中继 ↔ 内网主机，本机在移动热点）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 小请求成功率 | 11/20 | 20/20 |
| 小请求首字节 | 0.1s 或直接超时失败 | 稳定 65~81ms |
| 单流下载 | 340KB/s | 1.67MB/s |
| 池连接异常（日志） | 每 6~10 秒摘一条 | 无 |

## 进一步调参

| 场景 | 调整 |
|---|---|
| 高延迟链路想堆带宽 | `-pool` 从 6 调到 8~10（单条 TCP 受窗口限制，多连接轮询能叠加） |
| 时断时续的移动网络 | 保持默认心跳；把 `-open-timeout` 再降到 2s 更跟手 |
| MTU 踩坑（大包卡住、小包正常） | `-tun-mtu` 从 1400 降到 1280 |
| 大量短连接（网页加载） | 保持 `-fin-guard` 默认，别关 |

## 附：ping 的「3 快 1 慢」不是性能问题

见 [client.md](client.md#ping-的延迟为什么-3-个快1-个慢)。慢的那几个才是真实 RTT，快的是 3s 可达缓存的合成应答。
